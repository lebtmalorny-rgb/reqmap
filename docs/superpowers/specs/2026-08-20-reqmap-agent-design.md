# Проектирование агента `reqmap` для сопоставления требований с OpenStack Epoxy 2025.1

Дата: 2026-08-20  
Статус: утверждён пользователем 2026-08-20  
Язык пользовательской и эксплуатационной документации: русский

## 1. Назначение

`reqmap` — переносимый специализированный агент для автономного исследования требований к продукту на базе OpenStack Epoxy 2025.1.

Агент должен:

- принимать одно требование, набор требований или книгу XLSX;
- сохранять исходные формулировки и координаты строк без изменений;
- восстанавливать группы, родительские требования и подпункты;
- разбивать составные требования на атомарные проверяемые утверждения;
- сопоставлять каждое утверждение одному или нескольким компонентам;
- различать runtime-операции через OpenStack API и design-time настройки через `kolla-ansible reconfigure`;
- отдельно учитывать изменения хостовой ОС, для которых обязательны связь с `Kolla-Ansible` и указание затронутой подсистемы ОС;
- показывать, когда штатное сопоставление невозможно либо локальных доказательств недостаточно;
- создавать проверяемые XLSX, JSON, Markdown и журнал воспроизводимости;
- работать на обычном Linux без контейнерного runtime;
- запускаться напрямую либо через Codex/OpenCode;
- использовать внешний локальный LLM-сервер с OpenAI-compatible API.

## 2. Исходный контекст

В исходной папке находятся книги:

- `Требования к PV Stack v3.xlsx`;
- `для СБТ_clean.xlsx`.

Предварительный структурный анализ показал около 1950 строк данных. Встречаются:

- самостоятельные требования;
- иерархические идентификаторы;
- повторяющиеся идентификаторы родительского требования и его подпунктов;
- составные формулировки, затрагивающие несколько компонентов;
- частичные ручные пометки компонентов;
- требования к OpenStack API;
- требования к конфигурации сервисов;
- требования к хостовой ОС и инфраструктурной автоматизации.

Следовательно, модель «одна строка — один компонент» запрещена.

## 3. Основные архитектурные решения

1. Используется CLI-first архитектура.
2. `reqmap` владеет всей предметной логикой, вызовами внешней LLM, валидацией и экспортом.
3. Codex и OpenCode являются внешними интерфейсами и запускают `reqmap` через общий repo-scoped skill.
4. Каноническим результатом является JSON. XLSX и Markdown строятся из него.
5. MCP не входит в первую версию. Внутренние интерфейсы не должны мешать последующему созданию тонкого MCP-адаптера.
6. База знаний поставляется локально и версионируется отдельно от кода.
7. Сопоставление является many-to-many на уровне атомарных утверждений.
8. Все подтверждённые выводы обязаны ссылаться на локальный evidence.
9. При отсутствии достаточного evidence агент обязан воздержаться от утверждения поддержки.
10. Эталонный набор размеченных пользовательских требований не создаётся и не поставляется.

## 4. Границы системы

```text
Пользователь
    |
    +-- Codex/OpenCode --> .agents/skills/reqmap/SKILL.md --+
    |                                                       |
    +-- обычный shell ---------------------------------------+--> reqmap CLI
                                                                    |
                                                                    +--> локальная база знаний
                                                                    +--> внешний OpenAI-compatible LLM
                                                                    +--> валидатор
                                                                    +--> XLSX/JSON/Markdown/журнал
```

Модель, управляющая Codex/OpenCode, отвечает только за распознавание намерения, загрузку skill и запуск команды. Предметный анализ выполняет `reqmap`, поэтому прямой запуск, Codex и OpenCode используют один pipeline и один контракт результата. Текстовый вывод локальной LLM может различаться между запусками; клиент запуска не должен добавлять собственную предметную разметку. Параметры модели и поддерживаемый endpoint-ом `seed` фиксируются в manifest.

## 5. Компоненты

### 5.1. Input adapters

Обязанности:

- принимать текст из stdin или файла;
- читать XLSX без изменения источника;
- сохранять имя файла, лист, номер строки, исходный ID и исходный текст;
- назначать каждой исходной строке уникальный технический ID `REQ-0001`, `REQ-0002` независимо от наличия исходного ID;
- сохранять исходный ID отдельно и буквально, включая повторяющиеся значения;
- фиксировать hash входного файла.

Для XLSX используется входной профиль, задающий:

- включаемые и исключаемые листы;
- строку заголовка;
- колонку ID;
- колонку формулировки;
- необязательные колонки приоритета, ожидаемого результата, родительской связи и существующих ручных пометок.

Разрешено безопасное автоопределение известных заголовков. Если найдено несколько возможных колонок или структура неоднозначна, запуск останавливается с диагностикой и требованием указать профиль. Угадывание колонок запрещено.

### 5.2. Requirement parser

Обязанности:

- восстанавливать порядок строк;
- определять родительские требования и подпункты;
- объединять строки в группы без потери отдельных строк;
- передавать родительский текст как контекст;
- не наследовать автоматически компоненты или статусы родителя;
- не удалять полные или частичные дубли требований.

Существующие ручные пометки компонентов сохраняются как `source hints`. Они могут влиять только на порядок кандидатов и не являются `evidence` или подтверждённым сопоставлением.

### 5.3. Atomic decomposer

Обязанности:

- с помощью внешней LLM разбивать составное требование на атомарные утверждения;
- сохранять ссылку каждого атома на исходное требование;
- запрещать появление новых обязательств, которых нет в исходной формулировке;
- возвращать результат по строгой JSON-схеме.

### 5.4. Knowledge retriever

Обязанности:

- искать кандидатов по локальному каталогу компонентов и capabilities;
- учитывать синонимы, русские формулировки и технические идентификаторы;
- передавать модели только ограниченный набор релевантных evidence;
- не использовать доступ в Интернет во время штатного анализа.

Первая версия должна использовать детерминированный локальный поиск. Внешний векторный сервис не требуется.

### 5.5. LLM analyzer

Обязанности:

- выбрать один или несколько компонентов только из переданных кандидатов;
- определить роль каждого компонента;
- выделить отдельные runtime и design-time шаги;
- указать механизм реализации;
- определить источник реализации;
- вернуть evidence IDs и краткое обоснование;
- выставить `insufficient_evidence`, если доказательств недостаточно.

### 5.6. Validator

Обязанности:

- проверять JSON-схему;
- отклонять неизвестные компоненты и evidence IDs;
- проверять обязательные поля;
- применять fail-closed инварианты;
- вычислять итоговый статус требования из статусов атомов;
- проверять согласованность всех выходных артефактов.

### 5.7. Exporters

Обязанности:

- записывать канонический JSON;
- создавать XLSX из канонического JSON;
- создавать русский Markdown-отчёт;
- записывать журнал запуска и manifest воспроизводимости;
- никогда не изменять исходный XLSX.

## 6. Поток обработки

### 6.1. Preflight

До чтения требований проверяются:

- существование и версия базы знаний;
- валидность конфигурации;
- доступность OpenAI-compatible endpoint;
- доступность указанной модели;
- права на чтение входа и запись каталога результата.

Если preflight не пройден, предметный анализ не начинается.

### 6.2. Загрузка и структурирование

Вход преобразуется во внутренний формат. Исходный текст, ID, порядок и координаты сохраняются буквально. Парсер формирует дерево или группы только как дополнительный контекст.

### 6.3. Декомпозиция

Внешняя модель получает исходное требование, родительский контекст и строгую схему ответа. Она возвращает атомарные утверждения.

### 6.4. Поиск evidence

Для каждого атома retriever выбирает ограниченный набор компонентов, capabilities и evidence из локальной базы.

### 6.5. Сопоставление

Внешняя модель получает атом и найденные кандидаты. Она не вправе называть компоненты или evidence, отсутствующие в переданном наборе.

### 6.6. Валидация

Валидатор проверяет схему и предметные инварианты. Невалидная связь не попадает в подтверждённый результат.

### 6.7. Агрегация и экспорт

Результаты атомов агрегируются на уровне исходных требований. Все связи остаются доступными в нормализованном виде. После этого создаются артефакты.

## 7. Участие внешней модели

Внешняя локальная модель вызывается на двух ограниченных этапах:

1. декомпозиция составного требования;
2. семантическое сопоставление атома с найденными evidence.

Модель не используется для:

- чтения XLSX;
- вычисления ID и координат;
- проверки hash;
- поиска неизвестных компонентов вне базы;
- валидации ссылок;
- агрегации статусов;
- формирования структурных проверок артефактов.

Клиент модели конфигурируется через OpenAI-compatible параметры:

- `base_url`;
- `model`;
- имя переменной окружения для API key, если сервер его требует;
- timeout;
- число повторов;
- ограничения размера контекста и ответа;
- temperature, по умолчанию минимальная для детерминированного анализа.

Секреты не записываются в конфигурационные примеры и журнал запуска.

## 8. Каноническая модель результата

### 8.1. Независимые оси

Поддержка:

- `supported`;
- `partial`;
- `not_supported`;
- `insufficient_evidence`;
- `not_applicable`.

Источник реализации:

- `upstream`;
- `kolla_ansible`;
- `product_extension`;
- `external_component`.

Фаза:

- `runtime`;
- `designtime`.

Тип связи:

- `implements`;
- `configures`;
- `prerequisite`;
- `integrates`;
- `host_os_change`.

Сила доказательства:

- `direct`;
- `indirect`;
- `none`.

Состояние обработки:

- `completed`;
- `model_failed`;
- `validation_failed`;
- `skipped`.

Машинные enum-коды остаются английскими и стабильными. В пользовательских артефактах рядом выводятся русские отображаемые названия.

`insufficient_evidence` является результатом успешно выполненного анализа при нехватке предметных доказательств. Сбой модели или валидатора не должен маскироваться этим статусом: для него используется отдельное состояние обработки, а support status остаётся незаполненным.

Отсутствие найденного `evidence` не доказывает `not_supported`. Этот статус разрешён только при прямом отрицательном `evidence`, несовместимом `version constraint` или доказанном конфликте с обязательной частью требования. Во всех остальных случаях используется `insufficient_evidence`. Статус `partial` обязан явно перечислять поддержанные и неподдержанные либо неподтверждённые атомы.

### 8.2. Runtime и design-time

Runtime означает операцию, выполняемую через OpenStack API после развёртывания.

Design-time означает изменение конфигурации компонента с последующим `kolla-ansible reconfigure`.

Если требование содержит оба аспекта, создаются две отдельные записи, а не один непрозрачный статус `mixed`.

### 8.3. Хостовая ОС

Любое подтверждённое изменение хостовой ОС обязано содержать:

- компонент `Kolla-Ansible` как механизм доставки или автоматизации;
- конкретную подсистему ОС, например `chrony`, `nftables`, networking, kernel/sysctl или package management;
- отдельный implementation step;
- evidence.

Требование к хостовой ОС нельзя автоматически считать не относящимся к продукту.

### 8.4. Агрегация

Итоговый статус исходного требования вычисляется так:

- `not_supported`, если хотя бы один обязательный атом имеет `not_supported`;
- результат отсутствует, если хотя бы один обязательный атом имеет состояние обработки, отличное от `completed`, и нет подтверждённого `not_supported`;
- `insufficient_evidence`, если хотя бы один обязательный атом имеет `insufficient_evidence`, а `not_supported` отсутствует;
- `partial`, если хотя бы один обязательный атом имеет `partial`, а `not_supported` и `insufficient_evidence` отсутствуют;
- `not_applicable`, если все атомы имеют `not_applicable`;
- `supported`, если все обязательные применимые атомы имеют `supported`, а остальные имеют `not_applicable`.

Групповое представление является только агрегированным отчётом и не заменяет результаты отдельных строк. Список компонентов группы является объединением подтверждённых `mappings` дочерних требований, а статус вычисляется по тем же правилам приоритета. В `group record` обязательно сохраняются ID всех исходных строк.

## 9. Выходные артефакты

### 9.1. JSON

JSON является единственным каноническим результатом. Он содержит:

- metadata запуска;
- исходные требования и их `source hints`;
- группы и родительские связи;
- атомарные утверждения;
- mappings;
- runtime и design-time steps;
- evidence;
- ошибки и предупреждения.

### 9.2. XLSX

Создаётся отдельная книга с листами:

1. `Требования` — исходные строки, координаты, `parent/group IDs`, агрегированные компоненты и итоговые статусы.
2. `Атомарные утверждения` — связь атомов с требованиями.
3. `Сопоставления` — одна строка на связь «атом — компонент — фаза».
4. `Доказательства` — evidence ID, локальный источник и подтверждаемое утверждение.
5. `Запуск` — модель, версии, hashes, параметры и статистика.

Формулировки требований в XLSX не сокращаются и не перефразируются.

### 9.3. Markdown

Русский инженерный отчёт содержит:

- статистику требований и атомов;
- распределение по компонентам;
- runtime/design-time;
- требования к Kolla-Ansible и хостовой ОС;
- перечни `partial`, `not_supported` и `insufficient_evidence`;
- ошибки и предупреждения.

### 9.4. Manifest и журнал

Фиксируются:

- версия `reqmap`;
- версия базы знаний;
- модель и безопасные параметры endpoint;
- hashes входа и результатов;
- время запуска;
- итоговый статус `SUCCESS`, `PARTIAL` или `FAILED`;
- число повторных вызовов и ошибок модели.

## 10. База знаний Epoxy 2025.1

База знаний хранится в `knowledge/epoxy-2025.1/` и включает:

- реестр компонентов;
- capabilities;
- API operations;
- design-time options;
- Kolla-Ansible mappings;
- host OS subsystems;
- aliases и русские синонимы;
- evidence records;
- локальные snapshots или выдержки официальных upstream-источников, достаточные для аудита evidence;
- manifest версии и hashes.

Каждый evidence record обязан содержать:

- стабильный ID;
- компонент;
- локальный путь к источнику;
- раздел или точный locator;
- краткое атомарное утверждение;
- тип evidence;
- применимость к версии 2025.1;
- runtime/design-time признак, если применимо.

Для локального источника дополнительно фиксируются исходный официальный URL, дата получения, версия, hash и сведения о происхождении. Получение или обновление upstream-источников разрешено только в отдельном maintenance-окружении с доступом в Интернет. Runtime-пакет анализа использует уже собранный snapshot.

Обновление базы выполняется отдельным документированным процессом. Штатный анализ не изменяет базу знаний.

## 11. Сбои и восстановление

- Недоступная модель на preflight приводит к `FAILED` без начала анализа.
- Невалидный JSON модели допускает одну корректирующую попытку.
- Повторная ошибка выставляет атому `analysis_state=model_failed`, оставляет support status незаполненным и записывает диагностику; остальные требования продолжают обрабатываться.
- Неизвестный компонент или evidence отклоняется валидатором.
- Повреждённый входной XLSX приводит к `FAILED`; источник не изменяется.
- Результаты сохраняются по требованиям в рабочем каталоге запуска.
- Повторный запуск может продолжить обработку при совпадении hash входа, версии базы, модели и значимых параметров.
- Любой частичный результат явно маркируется `PARTIAL`.

## 12. Проверка качества без эталонного набора требований

Поставляются:

- unit tests парсеров, моделей данных, агрегации и exporters;
- property/invariant tests;
- контрактные тесты с имитацией OpenAI-compatible endpoint;
- интеграционные smoke tests на синтетических примерах;
- негативные синтетические тесты ложных сопоставлений;
- cross-artifact проверки JSON/XLSX/Markdown;
- тест автономной установки на чистом Linux-окружении.

Обязательные инварианты:

1. Исходный текст и порядок строк сохранены.
2. Все mappings ссылаются на существующие требования, атомы, компоненты и evidence.
3. Подтверждённый вывод без evidence запрещён.
4. Design-time step содержит `kolla-ansible reconfigure`.
5. `host_os_change` содержит `Kolla-Ansible` и подсистему ОС.
6. Агрегированный статус воспроизводится из атомов.
7. XLSX и Markdown воспроизводятся из канонического JSON.
8. В артефактах нет секретов конфигурации.
9. Количество исходных строк до и после обработки совпадает.
10. `insufficient_evidence` не используется для маскировки `model_failed` или `validation_failed`.
11. Неоднозначная структура XLSX не обрабатывается без явно заданного входного профиля.
12. Отсутствие найденного `evidence` не преобразуется автоматически в `not_supported`.
13. Ручные `source hints` не используются как `evidence`.
14. Дубли исходных требований не удаляются.
15. Выходной XLSX проходит проверку целостности ZIP/OOXML и независимое повторное чтение.

Негативные тесты обязаны защищать от широких ложных связей, включая:

- Horizon как доказательство любой GUI-функции;
- Octavia как механизм балансировки VM workload;
- Ceilometer как биллинговый компонент;
- PCI passthrough как достаточное доказательство vGPU.

Эти тесты являются синтетическими проверками правил, а не эталонной разметкой пользовательских требований.

## 13. Переносимость и установка

Первая версия поставляется как обычный Git-репозиторий для Linux без Docker/Podman.

Структура поставки:

```text
reqmap/
├── src/reqmap/
├── knowledge/epoxy-2025.1/
│   └── sources/
├── .agents/skills/reqmap/SKILL.md
├── vendor/wheels/
├── config.example.yaml
├── install.sh
├── README.md
├── INSTALL_OFFLINE.md
├── RUNBOOK.md
├── KNOWLEDGE_BASE.md
├── OUTPUT_SCHEMA.md
├── CLIENTS_CODEX_OPENCODE.md
└── tests/
```

Требования к установке:

- системный Python 3.11 или новее;
- Git для получения репозитория;
- доступ к локальному OpenAI-compatible endpoint;
- отсутствие обязательного доступа к PyPI или Интернету после получения репозитория.

`install.sh`:

- создаёт локальное virtual environment;
- устанавливает зависимости только из `vendor/wheels` с `--no-index`;
- проверяет CLI и конфигурацию;
- не устанавливает модель и не изменяет системный Python.

Для переносимости обязательные runtime-зависимости должны иметь universal pure-Python wheels. Нативные зависимости не входят в первую версию.

## 14. Интеграция с Codex и OpenCode

Общий skill располагается по пути `.agents/skills/reqmap/SKILL.md`.

Skill должен:

- распознавать запросы на анализ требований;
- принимать вставленный текст или путь к XLSX;
- проверять наличие установленного `reqmap`;
- безопасно передавать текст через stdin или временный структурированный input, не через хрупкую shell-подстановку;
- запускать CLI;
- показывать краткое резюме и пути к артефактам;
- не выполнять самостоятельное параллельное сопоставление компонентов.

Прямой запуск:

```bash
reqmap analyze requirements.xlsx --config config.yaml --output results/
```

Интерактивный запуск через stdin:

```bash
reqmap analyze --stdin --config config.yaml --output results/
```

MCP может быть добавлен позднее как адаптер над публичным Python API. Он не должен содержать отдельную предметную логику.

## 15. Язык документации и интерфейса

Обязательно на русском языке:

- `README.md`;
- инструкция автономной установки;
- руководство оператора;
- описание базы знаний и её обновления;
- описание схемы результатов;
- инструкции для Codex/OpenCode;
- troubleshooting;
- CLI help и пользовательские сообщения об ошибках;
- Markdown-отчёт;
- названия и отображаемые значения в XLSX;
- комментарии к конфигурационным примерам.

Без перевода сохраняются:

- имена OpenStack-компонентов;
- команды CLI;
- API paths и configuration keys;
- имена файлов и Python identifiers;
- стабильные машинные enum-коды;
- цитируемые технические идентификаторы из локальных источников.

## 16. Безопасность и конфиденциальность

- Штатный анализ работает без внешнего Интернета.
- Требования передаются только настроенному локальному LLM endpoint.
- API key читается из переменной окружения.
- Секреты не записываются в журнал, manifest или результаты.
- Исходные файлы открываются только для чтения.
- Временные файлы создаются внутри каталога запуска с ограниченными правами.
- Агент не выполняет OpenStack API operations и `kolla-ansible reconfigure`; он только классифицирует способы реализации.

## 17. Критерии приёмки первой версии

Первая версия считается готовой, когда:

1. Устанавливается на обычный Linux из клонированного репозитория без PyPI и контейнеров.
2. Принимает текст, набор требований и XLSX.
3. Поддерживает явные входные профили XLSX и останавливается при неоднозначном автоопределении колонок.
4. Не изменяет исходные XLSX и сохраняет все исходные строки.
5. Поддерживает many-to-many mappings.
6. Выводит отдельные runtime и design-time steps.
7. Design-time классифицируется через `kolla-ansible reconfigure`.
8. Изменения хостовой ОС связаны с `Kolla-Ansible` и подсистемой ОС.
9. Неизвестные предметные случаи получают `insufficient_evidence`, а сбои обработки — отдельные состояния `model_failed` или `validation_failed`.
10. Создаёт согласованные JSON, XLSX, Markdown и журнал запуска.
11. Работает напрямую, через Codex и через OpenCode с одним общим skill.
12. Вся пользовательская и эксплуатационная документация выполнена на русском.
13. Все автоматические структурные, контрактные, негативные и cross-artifact тесты проходят.
14. Полные и частичные дубли требований не удаляются и остаются отдельными исходными строками.
15. Групповая агрегация сохраняет ссылки на все исходные строки и не заменяет построчные результаты.
16. Ручные `source hints` сохраняются, но не используются как доказательство.
17. Отсутствие найденного evidence не классифицируется как `not_supported` без прямого отрицательного доказательства.

## 18. Явно исключено из первой версии

- MCP-сервер;
- Docker/Podman образы;
- запуск или поставка весов LLM;
- онлайн-поиск во время анализа;
- изменение исходных XLSX;
- выполнение конфигурационных изменений в OpenStack;
- выполнение `kolla-ansible reconfigure`;
- эталонный набор размеченных пользовательских требований;
- поддержка версий OpenStack, отличных от Epoxy 2025.1;
- web UI.
