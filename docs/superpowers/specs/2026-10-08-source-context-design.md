# Проверенный контекст исходных строк

Статус: **проект спецификации для согласования; реализация не начата**.
08.10.2026 пользователь согласовал принцип: исходные строки сохраняются
отдельно, контекст заголовков и условий присоединяется только через явно
проверенные связи. Этот документ уточняет поведение, формат и цену такого
решения; согласование принципа не является приёмкой описанного ниже кода.

Основание: [аудит реального корпуса](../../acceptance/2026-10-07-real-corpus-readiness.md),
[план исправлений](../plans/2026-10-05-reqmap-coverage-remediation.md),
[действующий контракт source binding](2026-10-05-obligation-binding-design.md).
Проверенная отправная точка — `45b4e62`: грамматика 1.2, binding engine 1.1,
legacy/deep results 1.1/2.1, MCP tool/workflow 2.0.

## Результат для пользователя

Пункт списка не получает подтверждение по API, если проверенный заголовок
требует GUI. В отчёте видны исходная строка, присоединённые условия, их
точные источники и причина результата. Ни строка, ни её цитата не переписываются.
Самостоятельная строка с подтверждённой независимостью сохраняет прежнюю
предметную семантику. Повторные ID и одинаковые тексты сохраняются раздельно.

**Существенное изменение по умолчанию:** если независимость или полный
контекст строки не проверены, её результат — `insufficient_evidence`, даже
когда собственная фраза полностью распознана. Это относится к XLSX, TXT и
inline `texts`; тип входа сам по себе не доказывает независимость строк.
Отсутствие карты не препятствует импорту, поиску, завершению анализа и экспорту.
Оно препятствует доказательному выводу. Общего переключателя «считать все
строки независимыми» без привязки к проверенному источнику не добавляется.

Цена решения — подготовка проверенной разметки конкретного входа. Карта может
покрывать только часть строк: остальные честно остаются непроверенными.
Автоматическая разметка независимости всех 1 949 строк не входит в этот этап.

## Почему отдельная карта

| Вариант | Следствие |
| --- | --- |
| Наследовать ближайший заголовок или повторный ID автоматически | Техническая близость подменяет проверку смысла; переносится чужой контекст |
| Доверить модели готовые смысловые поля | Модель сможет опустить неудобное условие, а валидатор примет её трактовку за факт |
| Проверенная карта входа и общий детерминированный resolver | Выбранный вариант: явно фиксируются связи и пределы человеческой проверки |

Карта описывает **что требуется**, а KB и каталог predicates — **чем это
подтверждается**. Карта контекста не является evidence реализации функции.
Она не содержит `supported`, evidence IDs, predicate IDs или правил обхода
валидатора. Хеш и подпись подтверждают целостность и происхождение разметки;
они не доказывают правильность человеческого толкования текста.

## Граница первого внедрения

Первое внедрение закрывает передачу проверенных ограничений к уже распознаваемым
действиям. Оно поддерживает:

- интерфейс `api` или `gui`;
- существующие типы условий: duration в целых миллисекундах, host_failure
  и gpu со значением `true`, с теми же операторами, что у текущей грамматики;
- несколько источников условий для одной строки, включая иной лист той же книги;
- явное решение о независимости строки либо о неразрешённой зависимости.

Произвольные сроки, кванторы, исключения, release/contour, идентичность
действующего компонента, объект и действие **не выводятся из родителя**.
Если они необходимы и не представлены собственным полным разбором строки,
запись остаётся unresolved. Присоединение контекста не превращает неразобранную
фразу в распознанную и не снимает собственное отрицание.

Расширение грамматики списков, новые API/GUI evidence, разметка всех исходных
книг, автоматическое понимание произвольного русского текста и UI редактора
карт — последующие задачи. OpenStack, Kolla и host actions не исполняются.

## 1. Неизменный вход и ссылки

Общий слой CLI/MCP формирует `SourceDocumentSnapshot` до технической группировки.
Он хранит исходные bytes и импортированные строки, а также:

| Идентификатор | Значение |
| --- | --- |
| `input_sha256` | SHA-256 исходных bytes; для inline texts — текущего canonical JSON списка |
| `input_profile_sha256` | SHA-256 canonical JSON полного нормализованного профиля импорта, включая defaults; `null` без профиля |
| `requirements_sha256` | SHA-256 canonical JSON упорядоченных импортированных записей |
| `source_kind`, `source_name` | Вид источника и имя, сохранённые импортом |

Запись для `requirements_sha256` включает технический ID, ordinal, координату,
source ID, полный text, source fields и hints. Вычисленные `parent_id` и
`group_ids` в этот digest не входят. Реальный порядок массива обязателен;
порядок ключей canonical JSON фиксирован существующим сериализатором.

`SourceRowRef` содержит технический `requirement_id`, полную координату
`source_name/sheet/row` и SHA-256 точного UTF-8 текста строки. Все поля должны
указывать на одну запись snapshot. Source ID не является адресом.
`SourceFragmentRef` добавляет `[start,end)` и буквальный `quote`; смещения
измеряются в Unicode code points, как у существующего `SourceSpan`.

Ссылка за пределы импортированного snapshot, в том числе на исключённый лист,
недопустима. Для такого контекста сначала требуется явно расширить импорт и
создать новую карту. Ссылки не открывают внешние файлы или URL.

В первом внедрении origin ссылается только на `Requirement.text` другой строки.
`source_fields` и hints сохраняются, но не превращаются в источник типизированных
условий автоматически. Если обязательное ограничение находится, например,
в колонке ожидаемого результата и пока не представимо разрешённой ссылкой,
контекст отмечается unresolved. Нельзя утвердить независимость, молча исключив
такое условие. Ссылки на отдельные дополнительные поля потребуют последующего
расширения контракта и импорта.

## 2. Формат и доверие к карте

В конфигурацию CLI и MCP добавляется необязательный `source_context_path`.
Он указывает на локальный JSON с `schema_version="1.0"`, идентификатором карты,
идентичностью источника из раздела 1 и массивом `rows`. Один файл относится
ровно к одному snapshot. Неизвестные поля, повторные ключи JSON и неоднозначные
записи отклоняются общим строгим loader.

Каждая запись `rows` содержит:

| Поле | Контракт |
| --- | --- |
| `target` | Полный `SourceRowRef` оцениваемой строки |
| `disposition` | `independent`, `linked` или `unresolved` |
| `review_state` | `draft` или `reviewed` |
| `reviewed_by`, `reviewed_at`, `reason_ru` | Автор, UTC-время и основание проверки; для draft автор/время проверки равны null |
| `context_complete` | Проверено, что все применимые внешние условия учтены; true требуется для independent/linked с reviewed |
| `links` | Явный полный набор непосредственно применимых связей |

`independent` имеет пустой `links`. `linked` имеет непустой `links`.
`unresolved` имеет `context_complete=false` и объяснение отсутствующей проверки;
её draft-ссылки, если есть, доступны только как заметки, без влияния на смысл.
Отсутствующая строка и любая запись `draft` получают состояние `unreviewed`.
Несколько записей на один target запрещены. Независимость проверяется в
контексте всего выбранного входа, а не по одному окончанию или длине фразы.

Каждая применимая связь имеет уникальный `link_id`, `origin: SourceFragmentRef`,
`field` (`interface` либо `constraint`) и типизированное `value`.
Для interface значение — `api`/`gui`; для constraint — объект
`name/operator/value/unit` из разрешённых выше типов. Источник семантического
значения — проверенная аннотация конкретной цитаты. Regex по слову GUI или
результат LLM сам по себе не переводит её в reviewed.
Для duration допустимы `operator=within`, `unit=ms` и canonical строка целого
числа от 0 до 999999999999 без лишних ведущих нулей. Для host_failure/gpu —
`operator=eq`, `value="true"`, `unit=null`. Другие комбинации отклоняются.

Проверяющий отвечает одновременно за применимость связи к target, её значение
и полноту внешних условий. Он читает весь исходный контекст, включая отрицания
и оговорки вокруг выбранного span. Если неизвестное условие нельзя представить
первым набором типов, запись должна быть unresolved; нельзя отбросить его и
утвердить оставшиеся связи. Ошибка такого ревью остаётся ограничением метода.

Карту утверждает пользователь либо явно уполномоченный сопровождающий.
Модель может подготовить draft. MCP не получает инструментов утверждения
карты или возможность передать свою карту в `reqmap_start_session`/mapping.
Свободные `clarifications`, `parent_session_id`, hints и имя рецензента в
proposal не создают проверенного контекста. Все эти сведения остаются данными.

В legacy действует доверие к локальному maintenance-файлу, выбранному
оператором в конфигурации. Это не защита от того, кто может менять конфигурацию
или одобренные файлы. В deep карта дополнительно требует detached OpenSSH
подписи своих точных bytes с namespace `reqmap-source-context`, проверяемой
существующим trust config и ожидаемой signer identity. Trust-файлы и ключи
автоматически не изменяются; расширение разрешённого namespace — действие
сопровождающего. Статус reviewed обязателен и при действительной подписи.
Файл подписи расположен рядом с картой с добавленным суффиксом `.sig`;
сам JSON не содержит путей к ключам или дополнительных trust-политик.

Чтение использует существующие проверки обычного файла, symlink и изменения
во время чтения. Каталоги записи не пересекаются с картой/подписью/trust.
Общий предел карты — 25 MiB, не более 64 ссылок на строку; обе границы
проверяются одинаково в CLI/MCP. Лимиты ответов действуют без тихой обрезки
цитат: возвращается явная ошибка размера, а не неполный доказательный контекст.

## 3. Разрешение контекста

`SourceBinding` продолжает сохранять исходные fragments и obligations своей
строки. К нему добавляется `SourceContextDecision`: состояние проверки,
digest карты/записи, применённые ссылки, диагностика и effective obligations.
Исходные semantic fields не перезаписываются; результат их уточнения хранится
отдельно. IDs и source quotes исходных атомов сохраняются.

Одна проверенная карта применяется ко всему snapshot перед mapping:

1. Проверить идентичность snapshot, координаты, hashes, spans, схему и trust.
2. Для каждой строки установить independent/linked либо unreviewed/unresolved.
3. Для reviewed linked проверить отсутствие self-links и циклов среди
   применимых связей. Не выполнять транзитивного наследования. Если влияет
   также заголовок более высокого уровня, для target нужна отдельная прямая
   ссылка на него; `context_complete` охватывает и этот выбор.
4. Построить эффективные обязательства из собственного разбора и всех
   применимых внешних ограничений. Связи первого внедрения относятся ко всем
   canonical обязательствам строки. Частичное применение к удобному атому
   запрещено; если разные части требуют разного контекста, строка unresolved
   до отдельного проверенного правила.
5. Выполнить обычные evidence gates и сопоставление predicates по эффективному
   обязательству. Карта не может повысить результат прежних проверок.

Правила объединения:

- Собственное `interface=unspecified` уточняется единственным проверенным
  внешним интерфейсом. Явные одинаковые значения сохраняются со всеми ссылками.
- Собственный API и внешний GUI, два разных внешних интерфейса или разные
  значения одного условия дают `SOURCE_CONTEXT_CONFLICT`. Приоритета ближайшего
  родителя, последней записи или формулировки модели нет.
- Разные разрешённые типы constraints добавляются совместно. Одинаковое
  semantic key учитывается один раз, но сохраняет все происхождения.
  Для duration сравнение точное: никаких неявных min/max, конвертации единиц
  или вывода о более сильном/слабом условии.
- `actor/action/object/direction/contour/phase/release` не меняются картой.
  Недостающие предметные поля и неразобранные части остаются препятствием.

При unreviewed, unresolved или conflict запрещены `supported`, `partial`,
`not_supported` и `not_applicable`; итог — `insufficient_evidence` с причинами.
Это запрет на вывод без полного обязательства, а не отрицание возможности.
Неизвестная формулировка по-прежнему хранится целиком как placeholder.

Использование строки как origin не удаляет её из анализа и не присваивает ей
автоматический `not_applicable`. Её собственный результат вычисляется отдельно;
контекстная аннотация не является доказательством поддержки заголовка. Новые
правила классификации строк как заголовков без собственного обязательства
не входят в первое внедрение.

## 4. Пример ожидаемого поведения

Синтетический список: отдельная строка задаёт GUI-интерфейс, следующая содержит
операцию изменения имени ВМ. Для второй reviewed linked с точной ссылкой на
первую задаёт `interface=gui`. При наличии только Nova API evidence результат
— `insufficient_evidence`, с указанием источника GUI-условия.

| Состояние входа/карты | Результат с корректным API evidence |
| --- | --- |
| Полная API-фраза, независимость reviewed | Прежний `supported`, если все остальные gates пройдены |
| Такая же фраза без карты либо без записи о ней | `insufficient_evidence`, контекст не проверен |
| Пункт без интерфейса, reviewed GUI-связь | `insufficient_evidence`, API не доказывает GUI |
| Пункт без интерфейса, reviewed API-связь | Может получить `supported` после остальных gates |
| Явный API в строке и reviewed GUI в контексте | `insufficient_evidence`, конфликт источника |
| Совпадает ID, но нет reviewed связи | Контекст не наследуется; без решения о независимости — insufficient |
| Правильная GUI-связь, но собственная фраза unresolved | `insufficient_evidence`, собственный текст не распознан |
| Неучтённая оговорка о сроке или работе при отказе | Карта unresolved, положительный вывод запрещён |

## 5. Общий runtime, replay и версии

Новые модели/loader/resolver целесообразно отделить в `source_context_models.py`,
`source_context.py` и `source_context_codec.py`. Это предлагаемые файлы;
детальные задачи реализации оформляются после согласования спецификации.
`binding_runtime.requirement_context` получает проверенный snapshot контекста;
`context_obligation` повторно строит effective obligation из него. Прямой вызов
validator без такого snapshot не означает независимость строки.

Общий resolver используется `pipeline.py`, `deep_pipeline.py`,
`agent_service.py`, `agent_context.py` и `agent_replay.py`. Технический
`grouping.py` не назначает reviewed-состояния. Модель выбирает существующие
canonical атомы и evidence/predicates, но не переписывает context fields.

При старте CLI run или MCP session карта целиком замораживается вместе с
входным snapshot: bytes, hash, нормализованные решения и сведения о проверке
подписи. Отсутствие карты тоже фиксируется как явное состояние. Seed новой
сессии имеет `seed_version=2` и обязательный context snapshot; текущие SQL
таблицы сохраняются, новый payload находится в существующем поле seed.

При replay resolver заново проверяет сохранённые bytes, ссылки и решения.
Исходные XLSX и внешний файл карты после старта не нужны. Изменённая на диске
карта не применяется к активной сессии: для исправленной разметки создаётся
новая сессия. Ответы показывают digest именно замороженной карты. Для deep
доверие к сохранённой подписи проверяется по текущему trust config; отозванный
signer препятствует продолжению активного анализа.

CLI сохраняет тот же snapshot контекста для resume; новый запуск с изменённой
картой получает другую подпись run и не использует прежние checkpoints.
`context_id` и контроль решения включают identity snapshot, digest карты,
target review и всех origin refs, типизированные ограничения и версию resolver.
Подмена строки, профиля импорта, связи или решения не проходит проверку.
`resolver_sha256` вычисляется по canonical JSON manifest с именами и hashes
трёх новых context-модулей, `binding_models.py`, `binding_engine.py` и
`binding_runtime.py`; этот набор зависимостей входит в контракт. Изменение
любого из них делает прежний активный контракт несовместимым.

| Контракт | Новая версия / поведение |
| --- | --- |
| Source context map / resolver | 1.0 / 1.0 с hash кода resolver |
| SourceBinding | 2.0, содержит исходный binding и контекстное решение |
| Binding engine | 2.0 |
| Грамматика собственной строки | Остаётся 1.2, если её код не меняется |
| Result schema legacy/deep | 1.2 / 2.2 |
| MCP tool/workflow | 3.0 / 3.0, прежние имена девяти tools |
| Proposal schema | 2, новые поля утверждения контекста не допускаются |
| Prompts decomposition/mapping/deep mapping | 2.1 / 1.4 / 2.2; описывают effective source и его ограничения |
| Старые активные сессии/checkpoints | Явная несовместимость, без миграции под новый смысл |
| Старые finalized outputs 1.0/1.1/2.0/2.1 | Read-only historical, проверка прежних artifact hashes; не пересчитываются |

Исторические seed payloads распознаются отдельной веткой decoder; отсутствие
нового поля не заменяется значением reviewed/independent. `get_result`
должен читать готовую старую публикацию без исполнения нового resolver;
`historical` определяется сравнением контракта, а не только schema 1.0/2.0.
Правила durable receipts, request IDs и sealed publication сохраняются.

## 6. Диагностика и пять файлов

| Код | Результат |
| --- | --- |
| `SOURCE_CONTEXT_UNREVIEWED` | Строка без утверждённой классификации: insufficient |
| `SOURCE_CONTEXT_UNRESOLVED` | Неполная связь/условие отмечены проверяющим: insufficient |
| `SOURCE_CONTEXT_CONFLICT` | Противоречащие ограничения источника: insufficient |
| `SOURCE_CONTEXT_INVALID` | Некорректная схема, тип, дубликат или неподдерживаемая аннотация: ошибка preflight |
| `SOURCE_CONTEXT_INPUT_MISMATCH` | Изменились input/profile/requirements hashes: ошибка preflight |
| `SOURCE_CONTEXT_REF_INVALID` | Чужая строка, неверная координата, hash или span: ошибка preflight |
| `SOURCE_CONTEXT_CYCLE` | Self-link/цикл применимых связей: ошибка preflight |
| `SOURCE_CONTEXT_UNTRUSTED` | Нет требуемой подписи/доверия deep: ошибка preflight либо active replay |
| `SOURCE_CONTEXT_CHANGED` | Сохранённое решение расходится с замороженным snapshot: ошибка replay/export |

Существующие `SOURCE_INTERFACE_UNPROVEN`, `SOURCE_CONDITION_UNPROVEN` и другие
предметные коды сохраняются, но могут ссылаться на внешний origin. Нельзя
показывать смещение родительской строки так, будто оно относится к target.
Диагностика получает явные `source_refs`; прежние `source_spans` относятся
только к собственной строке. `uncovered_context_refs` хранится отдельно от
собственных `uncovered` spans.

JSON содержит исходные и эффективные обязательства, решения проверки,
типизированные условия и полный набор source refs. Положительный аспект
сохраняет буквальную цитату своего атома и явные ссылки на применённый контекст;
он не отображается как безусловная поддержка оторванной цитаты.
Markdown и XLSX показывают рядом с атомом состояние проверки и конкретные
условия с координатами/цитатами. Прежние 5/7 листов сохраняются; новые колонки
не заменяют исходный текст и не прячут обязательные условия только в manifest.

`run.jsonl` и `manifest.json` содержат новый контракт, digest input/context и
resolver, коды диагностики и сведения о trust. В `result.json` сохраняется
вся нормализованная карта, включая непроверенные записи, чтобы экспорт не
зависел от внешнего файла. Пять прежних артефактов сохраняются без шестого
обязательного файла. Export validation и crosscheck сравнивают одинаковые
канонические решения, а не только совпадение статусов.

## 7. Критерии приёмки

До реализации фиксируется синтетический набор с независимыми ожиданиями:

- независимая API-строка с reviewed записью и та же строка без проверки;
- GUI-список с отдельным пунктом, два уровня заголовков и условие после списка;
- явный API против внешнего GUI, конфликт duration, два совместимых условия;
- неизвестная оговорка, отрицание, неизвестный объект, неоднозначный actor;
- обязательное условие в source field, которое нельзя выразить разрешённой
  ссылкой: unresolved вместо молчаливого удаления условия;
- одинаковые source IDs на разных листах, одинаковые цитаты в разных строках,
  несколько атомов в строке и сохранение всех обязательств;
- draft, пропущенная запись, чужой input, иной профиль, подменённые spans,
  исключённый лист, дубликат target/link ID, self-link, цикл и injection;
- попытка модели утвердить/убрать контекст, смешать одобренные и draft-связи
  либо представить заголовок как доказательство реализации;
- отсутствие/изменение/удаление внешнего файла после старта, порча snapshot,
  новая карта при новом запуске, отозванная deep-подпись;
- одинаковый результат legacy/deep и CLI/MCP, restart/replay/finalize,
  пять файлов, старые активные и finalized контракты.

Для воспроизведённого дефекта сначала наблюдается RED: оторванный пункт
получает supported. После исправления — GREEN: без reviewed решения
insufficient, с GUI-связью API evidence недостаточно, с independent/API
контролем прежнее положительное поведение сохраняется. Остальные ошибки
проверяются точным кодом и сохранностью всех source refs.

После контрактных тестов — полный suite и независимое ревью реализации.
Затем отдельный замороженный набор для живого клиента, с проверками
`reqmap_finalize(allow_partial=false)`, `reqmap_get_result` и artifact hashes.
При оценке реальных книг сначала утверждается карта конкретной выборки;
в метриках раздельны просмотренные строки, непроверенный контекст,
неразобранная собственная фраза и нехватка применимых evidence.
Результаты synthetic suite не выдаются за покрытие исходных 1 949 строк.

## Проверка проекта спецификации

Сверены текущие models, source binding, evidence gate, CLI/MCP contexts,
seed/replay и исторический get_result. Устранены неоднозначности: безопасное
поведение без карты определено для всех видов входа; нет автоматического
наследования по parent/ID; нет транзитивного применения непроверенных связей;
замороженная карта не меняется при редактировании внешнего файла; source refs
родителя не смешиваются со spans ребёнка; deep trust и старые отчёты отделены.
Это самопроверка проекта, не независимое ревью и не результат выполнения кода.
Проверки документации: `tests/test_docs_language.py` — **23 passed**;
относительные ссылки, отсутствие незаполненных маркеров и `git diff --check`
проверены. Runtime-тесты не запускались: реализация не менялась.

Следующий шаг после согласования этого файла — отдельный план реализации
с RED/GREEN проверками, миграцией контрактов и способом исполнения.
