# Связь исходного обязательства с доказательством

Статус: **контракт согласован, реализован в runtime второго этапа**.
Проверка и ограничения: [приёмка](../../acceptance/2026-10-05-obligation-binding-runtime.md).
Основание: [общий план](../plans/2026-10-05-reqmap-coverage-remediation.md),
[первый этап](../../acceptance/2026-10-05-evidence-scope-containment.md) и
[исследовательская проверка](../../acceptance/2026-10-05-obligation-binding-probe.md).

## Задача и граница

Положительный вывод должен подтверждать исходное обязательство, включая
действие, объект, отрицание, интерфейс и условия. Название сервиса, найденный
кандидат и выбранный агентом action ID не являются таким подтверждением.
Неизвестный текст сохраняется и получает `insufficient_evidence`.

Проект добавляет общий проверяющий слой к legacy и deep. Он распознаёт только
явно поддержанные конструкции и использует отдельную проверенную семантическую
разметку claims. Это ограниченная проверка соответствия; она не решает задачу
понимания произвольного русского текста. Рост количества отказов от вывода —
ожидаемая цена до пополнения правил и evidence.

Ограничения: Python 3.11+, без новых runtime dependencies и сетевых вызовов;
OpenStack Epoxy 2025.1; никакие OpenStack/Kolla/host actions не исполняются.
Исходные XLSX не меняются, не публикуются и не превращаются в fixtures.
Новые реальные claims и интерфейс импорта XLSX относятся к другим этапам.

## Что показал текущий код

- `mapping._atom_mapping_grounded` проверяет пересечение evidence с retrieval,
  а не соответствие полного source quote операции.
- `deep_mapping._candidate_for` и `_computed_support` проверяют связи
  action/effect/target, version, contour и evidence внутри KB. Содержимое
  исходного обязательства в вычисление поддержки не входит.
- `decomposition.accept_decomposition` требует цитату-подстроку, но допускает
  потерю оставшейся части строки и принимает модельный `mandatory=False`.
- `agent_replay` повторяет те же проверки. Это обеспечивает воспроизводимость,
  но воспроизводит и прежний неполный семантический контракт.

На synthetic specific evidence оба режима подтвердили создание VM и восемь
контрастных требований с тем же proposal. Простое переключение на deep
не исправляет этот дефект. Хеш, подпись и корректные ссылки подтверждают
целостность данных, а не истинность их семантической интерпретации.

## Сравнение подходов

| Подход | Что требуется | Преимущество | Ограничение |
| --- | --- | --- | --- |
| Ограниченный разбор только в legacy | Полные правила распознавания исходного текста и разметка legacy claims | Меньше затронутых интерфейсов | Дублирует понятия action/object/interface; deep остаётся уязвимым |
| Только existing deep actions/effects | Связи action/effect/target уже существуют | Точные идентификаторы операций и контуров | Не связывает исходную фразу с действием; нового source binding всё равно не избежать |
| Общий source binding, адаптеры legacy/deep | Один контракт обязательств, проверенный каталог предикатов и два адаптера | Одинаковая граница доказательности в CLI/MCP и двух профилях | Требует новых версий proposals/results и миграции активных сессий |

Рекомендация — третий подход. Для новых подробных пакетов знаний использовать
deep actions/effects как опору каталога, сохраняя legacy с тем же защитным
правилом. Автоматический перевод legacy claims в предикаты запрещён.
Модель может предлагать связи, но не утверждать собственную интерпретацию как
проверенную. Второй LLM-verifier тоже не становится детерминированной гарантией.

## 1. Источник и полнота обязательств

До mapping backend строит `SourceBinding` **для всей исходной строки**:

| Поле | Контракт |
| --- | --- |
| `contract_version` | `1.0` для нового binding-контракта |
| `requirement_id`, `coordinate` | Существующие технический ID и координата; source ID не уникальный ключ |
| `source_sha256` | SHA-256 точного UTF-8 `Requirement.text`, без нормализации |
| `fragments` | Упорядоченное полное разбиение строки на непересекающиеся `[start,end)` и буквальные `quote` |
| `obligations` | Обязательства с идентификаторами backend, ссылками на spans и полями ниже |
| `unresolved_fragments` | Все фрагменты без надёжного разбора; пустой массив — необходимое, но недостаточное условие поддержки |
| `grammar_version`, `grammar_sha256` | Точные версия и digest правил, применённых backend |

Смещения измеряются в Unicode code points Python `str`, не в байтах и не в
UTF-16. Инвариант: `text[start:end] == quote`; конкатенация всех fragments
восстанавливает исходную строку. Разрешённые пробелы и пунктуация получают
явный тип `syntax` и rule ID, а не исчезают. Значимые слова, числа, отрицания,
скобки, исключения, скрытые Unicode-символы нельзя молча отбросить.

Сначала применяется правило к **целой строке**, затем оно может породить
несколько независимых обязательств. Самостоятельное разбиение агентом не
позволяет отделить «при отказе» от операции. Неизвестная составная конструкция
целиком остаётся unresolved до появления проверенного правила.

Нераспознанная строка создаёт canonical placeholder-обязательство со всем
исходным span, `parse_state=unresolved`, пустыми semantic fields и
`mandatory=True`. Оно доступно retrieval и отчёту, но не доказательному выводу.
Это завершённый анализ с insufficient, а не ошибка модели. Для неоднозначного
разбора используется `parse_state=ambiguous`; известный однозначный разбор —
`parse_state=bound`. Backend не требует от модели выдумывать атом для unknown.

Новый atoms proposal содержит `source_span` и точную цитату для выбора уже
вычисленного backend обязательства. Одинаковая цитата в двух местах имеет
разные spans и ID. Пересечения и повтор одного вхождения отклоняются.
Неполный proposal отклоняется как `SOURCE_COVERAGE_GAP`; runtime после
исчерпания correction не публикует частичный набор атомов как полный анализ.
В каждом ответе/отчёте остаются исходная строка и конкретные пропуски.

`mandatory` вычисляет backend. В первом внедрении все распознанные обязательства
считаются обязательными; модельный `false` не принимается. Неизвестная
модальность — unresolved, а не optional. Родительский текст и hints остаются
контекстом поиска; они не восполняют отсутствующее обязательство без отдельного
контракта связей строк этапа 3.

## 2. Каноническое обязательство

`BoundObligation` содержит `obligation_id`, `source_spans`, `source_quote`,
`parse_state`, `rule_id`, `mandatory`, а также:

- `actor`, `action`, `object`: семантические значения из ограниченного словаря;
- `direction`: например capability или prohibition; запрет создавать не равен
  поддержке создания и не получается механической инверсией evidence polarity;
- `interface`: API, GUI либо явно `unspecified`;
- `contour`, `lifecycle_phase`, `release_scope`: требуемые контур, фаза и версия;
- `constraints`: условия применения, параметры, кванторы и ожидаемые эффекты,
  каждое со своими spans, типом, оператором, значением и единицей, если применимо.

Каждое поле получено из полного утверждённого правила и исходных spans.
Общие слова и IDs, присланные агентом, не могут заменить эту процедуру.
Разрешённая перефразировка явно связывается с тем же предикатом. Неизвестная
перефразировка может означать поддерживаемую функцию, но остаётся непроверенной.

Первый набор правил — замкнутая грамматика простого обязательства
`Nova должна создавать/удалять ... [через API/GUI] [условия]` и формы
`обеспечивать создание/удаление`. Псевдоним `ВМ` разрешён явно.
Исследовательский regex не переносится в runtime автоматически: правила
реализуются ограниченным кодом backend, версионируются и тестируются целиком.
Пользовательские regex и исполняемый код из snapshot не допускаются.

Для каждого однозначного правила нужен положительный пример и контрастные
примеры: отрицание, другой объект, неизвестный префикс/суффикс, число,
исключение, GUI/API, режим отказа. При неоднозначном разборе ни одно из
значений не выбирается по score: `SOURCE_AMBIGUOUS`, затем insufficient.

## 3. Семантический каталог доказательств

Добавляется отдельный локальный binding catalog, привязанный к точному digest
основного snapshot. Это не новый источник предметных утверждений.
Каждая `EvidencePredicate` включает:

- `predicate_id`, `evidence_ids`, `source_ids`, `locators` и hashes исходников;
- ссылку на capability; для deep — точные `action_ref`, `effect_ref`, `target_ref`;
- семантические action/object/direction/interface, contour/phase/version;
- явные assumptions и гарантируемые constraints/effects;
- `review_state=reviewed`, сведения о проверке и версию разметки.

Предикат вручную проверяют относительно конкретного claim/excerpt. Его
источник обязан остаться официальным, применимым и достаточно сильным по
правилам соответствующего профиля. Context evidence не получает предикат,
дающий подтверждение. Неразмеченная specific запись доступна поиску, но
не подтверждает соответствие исходному обязательству.

Legacy adapter проверяет владельца, capability/evidence/source и все правила
первого этапа. Deep adapter дополнительно проверяет точные relations и
подписанный snapshot. Наличие action/effect не заполняет семантические поля
автоматически. Имена сущностей, `terms` и locator не служат доказательством.

Каталог имеет `binding_schema_version=1`, `knowledge_sha256`, `catalog_id`,
`release_scope`, `predicates.jsonl`, manifest со списком файлов и hashes.
Config получает необязательный `binding_catalog_path`. Отсутствие каталога
разрешает анализ и retrieval, но даёт `BINDING_CATALOG_MISSING` и insufficient
для доказательных выводов. Повреждённый или относящийся к другой KB каталог —
ошибка preflight, а не тихое переключение к старой проверке.

Legacy использует тот же локальный maintenance trust, что и KB, с проверкой
digest и привязки snapshot. Deep требует подпись manifest тем же утверждённым
набором signers; namespace `reqmap-obligation-binding`. Это расширение trust
для нового артефакта, а не утверждение истинности claims по наличию подписи.
Исходные схемы KB v1/v2 не переписываются: их loaders остаются отдельными,
новый catalog loader проверяет дополнительный контракт.

## 4. Решение о поддержке

`check_binding` сопоставляет backend-обязательство с выбранными применимыми
предикатами. Проверяет действие, объект, direction, interface, phase, contour,
release и **все** ограничения. `unspecified` не требует конкретного интерфейса;
явный GUI не подтверждается существованием API. Неявный runtime не означает
поведение при отказе. Узкое доказательство при условии P не доказывает
безусловное требование.

Первое внедрение сравнивает условия точно по типизированным значениям.
Семантические импликации численных границ, единиц и различных предусловий
не угадываются. Они требуют отдельного правила с проверенной областью
применимости. Например, `за 1 мс` в прототипе не подтверждает другую строку
`за 2 мс`, хотя отдельная формальная модель метрики могла бы разрешить вывод.
Это сознательная неполнота, не отрицание поддержки.

Для первого внедрения один проверенный предикат должен покрыть обязательство
целиком. Нельзя сложить «создание по API» и «удаление по GUI» в «создание по GUI»;
нельзя объединять разные условия экспериментов в новую общую гарантию.
Разные предикаты могут подтверждать разные независимые обязательства.

`BindingDecision` хранит статус, полные predicate/evidence refs, диагностику
по полям и непокрытые исходные spans. Условно подтверждённое ядро сохраняется
только как кандидат, без `supported` для всего условного обязательства.
Supported aspects строит backend из доказанных обязательств, а не из свободного
текста агента.

Новая проверка не повышает статус прежнего evidence validator. `supported`
разрешён только при выполнении обеих проверок и полном покрытии источника.
Существующий приоритет агрегирования сохраняется: непроверенное обязательство
даёт insufficient, а не новый `partial`. `not_supported` требует применимого
отрицательного claim для этого же полного предиката. Иная версия источника
сама по себе не доказывает `not_supported`. `not_applicable` нельзя получить
из пустого retrieval или заявления агента; нужен явный проверенный scope rule.

## 5. Диагностика

| Код | Значение |
| --- | --- |
| `SOURCE_SPAN_INVALID` | Неточная цитата/смещение, повтор или пересечение вхождений |
| `SOURCE_COVERAGE_GAP` | Часть исходной строки не представлена в proposal |
| `SOURCE_UNPARSED`, `SOURCE_AMBIGUOUS` | Нет полного однозначного правила |
| `SOURCE_CONTEXT_REQUIRED` | Распознанная конструкция требует отсутствующего контекста |
| `SOURCE_ACTION_UNPROVEN`, `SOURCE_OBJECT_UNPROVEN` | Доказательство относится к иному действию/объекту |
| `SOURCE_DIRECTION_UNPROVEN`, `SOURCE_INTERFACE_UNPROVEN` | Не подтверждены direction или интерфейс |
| `SOURCE_CONDITION_UNPROVEN` | Не покрыто условие, параметр, фаза или эффект |
| `EVIDENCE_MISSING`, `EVIDENCE_CONTEXT_ONLY` | Нет доказательства либо есть только общая справка |
| `EVIDENCE_VERSION_MISMATCH`, `EVIDENCE_CONTOUR_MISMATCH` | Доказательство неприменимо |
| `BINDING_CATALOG_MISSING`, `BINDING_UNREVIEWED` | Нет проверенной семантической разметки |
| `EVIDENCE_CONFLICT` | Применимые доказательства противоречат друг другу |

Каждая диагностика содержит code, `message_ru`, requirement/obligation ID,
поле, source spans и относящиеся к ней evidence refs. `SOURCE_UNPARSED` может
указывать всю строку; нельзя обещать точную локализацию неизвестного смысла.
Диагностика зависит от исходных данных и выбранных evidence, а не от заявленного
агентом статуса. Поэтому `EVIDENCE_CONTEXT_ONLY` одинаково видна при предложенных
`supported` и `insufficient_evidence`, закрывая Minor первого этапа.

## 6. Совместимость и отчёты

| Граница | Изменение |
| --- | --- |
| KB v1/v2 | Исходные файлы и schemas сохраняются; каталог привязан к digest |
| Proposals | Явный `proposal_schema_version=2`; atoms выбирают canonical source spans, mapping выбирает obligation/predicate refs |
| Result JSON | Legacy `1.1`, deep `2.1`; добавляются source bindings и binding decisions |
| Prompts | Новые decomposition/legacy/deep prompt versions с новым response contract |
| Context/resume | Подпись включает source/KB/catalog/grammar hashes, binding engine version и proposal/result versions |
| Активные старые сессии | Явный `SESSION_CONTRACT_MISMATCH`; нужен новый анализ, без перепроигрывания под новым смыслом |
| Готовые старые отчёты | Сохраняются как исторические с прежней schema; не объявляются перепроверенными |
| Экспорт | Те же пять файлов; сведения о непокрытых spans и причинах видны во всех предметных форматах |

CLI и MCP вызывают один backend. Повторное чтение proposal, replay, finalize
и export не обходят binding. Отсутствующие version/hash fields старого
checkpoint означают несовместимость, а не default к новому контракту.
API инструменты сохраняют имена; payload schemas явно меняют версию.

Legacy XLSX сохраняет пять листов, deep — семь. Лист атомов получает
source spans и coverage, таблицы сопоставлений/ответственности — predicate refs
и непокрытые условия; diagnostics deep остаётся отдельным листом. JSON хранит
полные структурированные записи, Markdown показывает исходную цитату и gaps.
`run.jsonl` и manifest содержат версии/digests и диагностические коды без
секретов. Crosscheck сравнивает одни и те же canonical decisions.

## 7. Приёмка и что пока не доказано

Воспроизведение в `tools/research/obligation_binding_probe.py` отделено от
runtime. Оно проверяет 28 фраз в двух профилях, восемь controls по evidence и
пять controls покрытия текста. Это проверка конечной грамматики на synthetic
данных, без реальной базы предметных предикатов, MCP-интеграции и LLM.
Пять положительных случаев и 23 воздержания не являются метрикой качества
на пользовательских XLSX. Ошибка неизвестной допустимой перефразировки
ожидаемо снижает полноту, а не превращает функцию в неподдерживаемую.

До внедрения нужны RED/GREEN регрессии исходной потери условий, совпадение
CLI/MCP после replay/finalize, смена контекста при изменении правил, проверка
старых сессий и пяти файлов. Предметное наполнение KB и настоящая IDE-приёмка
остаются этапами 4–5. Прототип не следует копировать в production как готовый
семантический validator.
