# План исправления доказательности и покрытия reqmap

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans
> to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax
> for tracking.

**Goal:** Положительный статус подтверждает исходные обязательства применимыми
доказательствами; неполное покрытие и ошибки импорта имеют конкретную диагностику.

**Architecture:** Сохраняются локальная версионированная KB, общий backend для
CLI/MCP и неизменяемые источники. Retrieval предлагает кандидатов; проверка
доказательств отдельно устанавливает применимость к действию и условиям атома.
Структурированные actions/effects профиля deep рассматриваются как существующая
основа, но не считаются проверенными на реальном корпусе автоматически.

**Tech Stack:** Python 3.11+, pytest, существующие legacy/deep loaders, MCP stdio,
JSON/JSONL snapshots, read-only XLSX input.

**Spec:** [Аудит и критерии исправления](../../acceptance/2026-10-05-requirements-coverage-audit.md).

Это приоритизированный план корректирующих работ по результатам исследования.
Первый этап реализован согласно
[отдельному контракту](../specs/2026-10-05-evidence-scope-containment.md).
Результаты проверок — в [отчёте](../../acceptance/2026-10-05-evidence-scope-containment.md).
Исследовательская часть этапа 2 подготовлена:
[проект контракта](../specs/2026-10-05-obligation-binding-design.md),
[прототип и результаты](../../acceptance/2026-10-05-obligation-binding-probe.md),
[план внедрения](2026-10-05-obligation-binding-implementation.md).
Контракт согласован и внедрён в legacy/deep, CLI/MCP и отчёты 1.1/2.1.
Проверки и границы: [приёмка runtime](../../acceptance/2026-10-05-obligation-binding-runtime.md).
Этап 3 выполнен: [профили XLSX и проверка исходных книг](../../acceptance/2026-10-07-xlsx-input-profiles.md).
Этапы 4–5 **не выполнены**. Конечная грамматика прототипа не является
универсальной семантической проверкой произвольного русского текста.

## Общие ограничения

- OpenStack Epoxy 2025.1; online-получение источников только при сопровождении KB.
- Исходные XLSX не изменяются и не публикуются; пользовательские строки не становятся golden fixtures.
- Повторные исходные ID не удаляются; технический ID и координата каждой строки сохраняются.
- Source hints и project policy не являются самостоятельным доказательством реализации.
- Неизвестное поведение означает `insufficient_evidence`; `not_supported` требует применимого отрицательного доказательства.
- Новые claims содержат точный locator, version, excerpt, provenance и hashes.
- Ни анализ, ни проверки не исполняют OpenStack/Kolla/host actions.
- Semantic acceptance, тесты контрактов и integrity snapshot отчитываются раздельно.
- Изменения KB выполняются в maintenance-ветке; snapshot обновляется атомарно.

## Особое внимание при ревью

1. Известное имя компонента плюс выдуманное действие: не получать `supported`.
2. Поддерживаемое действие плюс недоказанное численное ограничение: не подтверждать целое.
3. Отрицание или замена объекта при прежних ключевых словах: не наследовать старый вывод.
4. Заголовок, продолжение и повторный ID: сохранять каждую строку и границу её контекста.
5. GUI/продуктовое требование при наличии backend API: требовать доказательства заявленного интерфейса.

## Этап 2. Спроектировать связь обязательства с доказательством

**Файлы для анализа:** `src/reqmap/models.py`, `knowledge_v2.py`,
`mapping.py`, `deep_mapping.py`, `decomposition.py`, `proposals.py`,
`prompts.py`, `agent_context.py`, `OUTPUT_SCHEMA.md`.

**Вход:** провалы из этапа 1 и небольшой синтетический набор действий,
отрицаний, объектов, параметров и численных ограничений.
**Выход:** отдельная спецификация контракта и проверяемый прототип до
производственного изменения схемы. Строгое сравнение слов не выдаётся за
универсальное доказательство смысла.

- [x] Сравнить два решения: ограниченный детерминированный разбор известных
  формулировок в legacy и использование существующих structured actions/effects
  в deep. Показать, как каждое отклоняет неизвестные условия в исходной цитате.
- [x] Зафиксировать обязательные поля связи: неизменная исходная цитата,
  действие, объект, ограничения, evidence refs и непокрытые части. Указанный
  агентом action ID сам по себе не подтверждает соответствие цитате.
- [x] Проверить контрастные пары: обычное действие / выдуманное действие;
  иной объект; отрицание; дополнительное условие времени; API / GUI;
  обычная операция / поведение при отказе. Вторая формулировка не должна
  автоматически наследовать доказательство первой.
- [x] Проверить допустимые перефразировки без изменения обязательств.
  Незнакомые конструкции сохраняются как непокрытые; запрещено отбрасывать слова,
  числа и отрицания ради совпадения с capability.
- [x] Определить diagnostics отдельно для отсутствия evidence, неприменимой
  версии/контура, неподтверждённого действия и непокрытого условия.
  Они должны доходить через общий backend до CLI/MCP и всех отчётов.
- [x] Зафиксировать совместимость snapshots, proposals, context IDs, resume и
  export schema; записать миграцию и критерии RED/GREEN в отдельный план внедрения.

## Этап 4. Наполнять evidence по повторно используемым возможностям

**Файлы:** `knowledge/epoxy-2025.1/` либо отдельный утверждённый deep snapshot,
`tools/kb/`, `tests/test_epoxy_snapshot.py`, `tests/test_retrieval.py`,
новый synthetic corpus regression fixture, `KNOWLEDGE_BASE.md`.

**Вход:** контракт этапа 2 и семейства пробелов из аудита.
**Выход:** небольшие проверенные пакеты claims, каждый со своим regression set.

- [ ] Первый пакет: создание/чтение/изменение/удаление ресурсов compute,
  network и storage. Затем identity/access, host/deployment, HA/migration,
  monitoring и GUI. Приоритет определяется реальными обязательствами,
  а не числом keyword hits в поиске.
- [ ] Для каждой возможности проверить официальные источники версии 2025.1:
  действие, объект, параметры, условия, ограничения и отрицательные доказательства.
  Одна общая страница сервиса не подтверждает весь пакет.
- [ ] Разделить API, GUI, продуктовые расширения и внешние компоненты.
  Отсутствующие продуктовые источники отмечать как пробел, без подмены OpenStack evidence.
- [ ] Пополнять retrieval terms только после создания доказанной возможности.
  Проверять синтетические эквиваленты найденных промахов: AD/LDAPS → Aodh,
  LACP → Cinder, создание порта без явного названия Neutron.
- [ ] На каждый claim добавить положительный случай и близкий неподтверждённый
  случай с иным объектом/условием/версией. Проверить как нахождение кандидата,
  так и итоговый статус через общий backend.
- [ ] Пересобрать hashes, выполнить `knowledge validate` и предметное ревью.
  Для deep дополнительно подготовить подпись и trust по `KNOWLEDGE_BASE.md`.
- [ ] Фиксировать каждый пакет отдельным коммитом вместе с snapshot metadata.

## Этап 5. Измерить результат через настоящий клиент

**Файлы:** `tests/fixtures/agent_eval.json`, `docs/acceptance/`, `README.md`.

**Вход:** исправленный backend, утверждённый snapshot и новый install пакета.
**Выход:** воспроизводимая предметная приёмка с честным знаменателем метрик.

- [ ] Подготовить synthetic eval по семействам, включая составные требования,
  перефразировки, ambiguity, negative evidence, conflicts, injection,
  выдуманное действие, численные условия и границы GUI/API.
- [ ] Сначала проверить baseline backend, затем выполнить eval настоящим
  агентом в VS Code. Scripted proposals не подменяют этот запуск.
- [ ] Записать model/client versions, snapshot/code hashes, prompt, session IDs,
  атомы, evidence и hashes пяти файлов.
- [ ] Отдельно посчитать сохранённые обязательства, необоснованные положительные
  выводы, необоснованные отрицательные выводы, воздержания и долю обработанных строк.
  Доля воздержаний не равна доле неподдерживаемых функций.
- [ ] Для локальных исходных наборов сначала согласовать контекст и трактовку
  составных строк, затем анализировать. Отчёт о качестве привязывать к реально
  просмотренным результатам; масштабирующий тест не считать предметной приёмкой.
- [ ] Обновить документацию, опубликовать только предназначенные для репозитория
  артефакты и проверить удалённый SHA.

## Критерий завершения всей программы

На зафиксированном проверочном наборе нет необоснованных положительных выводов,
обязательства не потеряны, каждая положительная связь прослеживается до
применимого claim и его источника. Все непокрытые условия явно перечислены.
Это подтверждение качества на указанном наборе, а не гарантия полного
покрытия всех возможных требований OpenStack.
