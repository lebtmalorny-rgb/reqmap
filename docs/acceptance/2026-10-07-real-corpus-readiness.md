# Готовность к анализу исходных XLSX после пакета Keystone

Повторно проверены **1 949 строк** двух исходных книг на коде
`279b50120f22623f3155ce3df1d8aab222e5dedd`. Импорт сохраняет текст, порядок,
исходные ID и координаты. Текущая грамматика целиком распознаёт **одну строку**,
остальные **1 948** представлены целыми неразобранными фрагментами.

Единственная распознанная строка — пункт списка о портале. В отрыве от
окружающего GUI-контекста валидатор принимает положительное сопоставление
с Nova API. Поэтому даже это совпадение не является доказательством полного
требования исходной книги. Следующий приоритет — проверяемый контекст исходных
строк, затем расширение разбора и предметных доказательств.

Это статическая проверка текущего импорта, поиска, разбора и отдельного
backend-сценария. Полный анализ книг настоящей моделью не выполнялся;
процент функционального покрытия не установлен. Успешные синтетические
[API](2026-10-07-api-live-eval-role-fix.md) и
[Keystone](2026-10-07-keystone-live-eval.md) прогоны остаются действительными
для своих наборов.

## Метод

Использованы исходные A/B и явные профили из
[приёмки импорта](2026-10-07-xlsx-input-profiles.md). Каждая строка заново
прочитана штатным `load_xlsx`; текст, source ID, порядок и координаты совпали
с сохранённым построчным аудитом 05.10.2026. SHA-256 книг совпали до/после
чтения и с прежними значениями. Нового независимого чтения другим XLSX-парсером
в этом аудите не было; оно выполнено на этапе приёмки импорта.

Для всех строк вызваны `bind_source`, `canonical_atoms` и
`retrieve(kb, text, (), 8)`. Проверено восстановление полной строки из fragments,
точность source spans и source hashes. Родительский текст не добавлялся в
исходную цитату, hints и прежние keyword-семейства не использовались как
доказательство. Неразобранный фрагмент является техническим placeholder,
а не утверждением, что строка содержит ровно одно смысловое обязательство.

Дополнительно `check_binding` проверил все 28 predicates для каждого
канонического обязательства с искусственно выбранным полным набором
доказательств каждого predicate и исходным статусом `supported`.
Это структурная верхняя граница применимости каталога: она не проверяет
выбор настоящей модели и не присваивает строкам итоговые support statuses.

Последние три категории поиска дают 1 949 строк. Категория specific является
подмножеством official, а не дополнительной категорией. Поисковое совпадение
не устанавливает применимость доказательства: среди примеров есть название
сервиса без действия и требование миграции с найденным CRUD evidence.

число строк без кандидатов уменьшилось с 471 до 414, с official evidence —
выросло с 581 до 677. Это изменение поиска после всех последующих пакетов,
а не измеренное улучшение функционального покрытия или заслуга одного Keystone.

## Воспроизведённая потеря контекста

В B1:14 находится пункт об изменении имени ВМ. B1:8 вводит список возможностей
портала, B1:15 поясняет сценарии портала, B1:3 задаёт GUI-контур раздела.
Исходные формулировки и имена книги остаются только в локальных материалах.

Проверка `build_groups` связывает пункт с общей duplicate-ID группой и
техническим родителем B1:3. Даже у такого обогащённого `Requirement`
`bind_source` учитывает только собственный текст строки. Для изолированного
пункта получается `interface=unspecified`; положительный API-predicate
разрешён действующим контрактом для такого интерфейса.

Через `accept_mapping` переданы одинаковые grounded описание роли, операция
`PUT /servers/{server_id}`, `E-NOVA-VM-RENAME` и `P-NOVA-VM-RENAME`:

| Вход диагностической проверки | Итог backend |
| --- | --- |
| Исходный пункт B1:14 в изоляции, с технической группой и parent ID | `supported` |
| Синтетическая самостоятельная операция с явным GUI | `insufficient_evidence`, `SOURCE_INTERFACE_UNPROVEN` |
| Синтетическая самостоятельная операция с явным API | `supported` |

Это воспроизводимый риск ложного подтверждения пункта в контексте книги.
Он не означает, что настоящая модель уже сделала такой вывод: proposals
созданы проверочным скриптом, MCP-финализация этого случая не выполнялась.
Сам API-predicate здесь корректен; потеря GUI-условия возникает до его проверки.

Причина прослежена по коду: [grouping.py](../../src/reqmap/grouping.py) строит
технические связи, [decomposition.py](../../src/reqmap/decomposition.py)
определяет parent text только как неавторитетный контекст,
[binding_source.py](../../src/reqmap/binding_source.py) разбирает одну строку,
[binding_engine.py](../../src/reqmap/binding_engine.py) допускает positive API
для `interface=unspecified`. Контракт проверенной связи обязательств между
строками ещё не реализован. Простое разрешение конечной точки с запятой или
расширение словаря увеличит число распознанных пунктов, сохранив этот риск.

## Следующий этап

Рекомендуемый порядок работ:

1. Согласовать трактовку заголовков, подпунктов и общих условий. Сохранить
   каждую исходную строку отдельно; проверенные связи должны ссылаться на
   конкретные координаты, spans и hashes. Один повторный ID не подтверждает
   смысловую связь. Несколько источников ограничений не сводятся автоматически
   к одному полю `parent_id`.
2. Описать контракт того, как проверенный контекст ограничивает обязательство
   и отображается в результате. Непроверенная зависимость не должна приводить
   к положительному выводу, игнорирующему возможное условие. Автономные строки
   должны сохранять прежнюю семантику. Требуются тесты CLI/MCP, resume/replay,
   export и несовместимости прежних активных контрактов.
3. После этого расширять полные правила разбора типовых списков и составных
   требований, не теряя отрицания, параметры, интерфейс и условия. Примеры
   для публикуемых тестов создавать синтетически, без копирования книг.
4. На согласованной выборке исходных строк измерить фактический результат
   настоящим клиентом. Новые пакеты evidence выбирать по оставшимся
   предметным пробелам. Product GUI требует собственных источников.

Это рекомендация по следующему контракту, не утверждённая новая спецификация.
Код, KB, конфигурация и исходные книги в этом аудите не менялись. Не запускались
модель, инфраструктура и `reqmap analyze`.
