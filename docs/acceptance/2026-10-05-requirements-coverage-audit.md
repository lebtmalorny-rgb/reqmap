## Метод и границы

1. Прочитаны все видимые листы двух исходных XLSX без сохранения книг.
   SHA-256 каждого файла до и после чтения совпал.
2. Для файла A использованы ID в колонке A, текст в B, данные со строки 2.
   Для B — ID в B, текст в C, данные со строки 3. Эти позиции проверены по
   фактической структуре книг. Пустые ячейки текста пропущены, повторные ID сохранены.
3. Для каждой непустой строки вызван штатный `retrieve(kb, text, (), 8)`.
   Ручные пометки компонентов не использованы. Разбиение на атомы, группировка
   и добавление родительского контекста на этом шаге не выполнялись.
4. Отдельно просмотрены характерные строки из разных областей и их evidence.
   Это выборочная предметная проверка, а не ручная разметка всех строк.
5. Через `accept_mapping` проверены намеренно неверные синтетические proposals.
   Один случай дополнительно проведён через `AgentService` до финализации.
   Это проверка backend, не результат генерации настоящей модели.

Имена, исходные тексты и полная построчная выгрузка пользовательских книг не
публикуются. Локальный каталог `results/coverage-audit-2026-10-05/` содержит
`audit.py`, `summary.json`, `rows.jsonl`, `probes.json`, `scope-probes.json` и
`service-probe.json`. В нём сохранены реальные координаты, hashes и параметры
извлечения. Ни одна строка аудита не получает автоматический support status.

## Подтверждённый дефект валидатора

Для трёх синтетических требований использовано одно и то же тестовое proposal
из `_supported_nova_mapping()` в `tests/test_acceptance.py`. Роль, шаг и
`supported_aspects` содержат `Compute instances через REST API`; cited evidence
— `E-NOVA-SCOPE-001`. Менялось только значение `api_operation`.

| Исходное обязательство | `server` | `Compute instances через REST API` | `POST /servers` |
| --- | --- | --- | --- |
| Создать ВМ через Nova REST API | `insufficient_evidence` | `supported` | `insufficient_evidence` |
| Квантовая телепортация ВМ через Nova | `insufficient_evidence` | **`supported`** | `insufficient_evidence` |
| Гарантированное создание ВМ за одну миллисекунду | `insufficient_evidence` | **`supported`** | `insufficient_evidence` |

Последний столбец показывает отсутствие этой строки операции в текущем
корпусе evidence, а не оценку реального API Nova. Во втором столбце результатов
общая фраза capability ошибочно заменяет доказательство исходного обязательства.

Аналогичный proposal, где роль/шаг/операция равны названию capability, был
составлен для каждого из 22 сервисов. Все **22 из 22 специально составленных
неверных proposals** получили `supported` на требование о телепортации.
Это показатель воспроизводимости конкретного дефекта, не частота ошибок модели.

Через `AgentService` случай Nova также дошёл до пяти файлов:
`run_status=SUCCESS`, статус требования `supported`, `allow_partial=false`.
Следовательно, дефект не устраняется финализацией или экспортом.

Причины в [mapping.py](../../src/reqmap/mapping.py):

- `_atom_mapping_grounded` проверяет совпадение component/evidence с retrieval,
  но не устанавливает, что evidence доказывает действие и ограничения атома.
- `_runtime_operation_grounded` запрещает небольшой список общих слов, однако
  любую другую дословную фразу из корпуса может принять за API-операцию.
- `_semantic_text_grounded` проверяет слова роли и шага, сформулированных агентом.
  Агент может заменить требование общим описанием и пройти эту проверку.
- Та же проверка требует буквального присутствия слов и может отклонять
  перефразировки. Ослабление лексического правила само по себе не исправит
  связь с исходным обязательством.

Таким образом, одной подсказки «указывай точную операцию» или добавления
Nova evidence недостаточно. Требуется проверять покрытие исходного действия,
объекта, отрицаний, численных условий и других обязательных ограничений.

## Воспроизведение без модели и инфраструктуры

Из корня checkout запустить:

```bash
PYTHONPATH=src:. .venv/bin/python - <<'PY'
from pathlib import Path
from reqmap.knowledge import load_knowledge
from reqmap.mapping import accept_mapping
from reqmap.retrieval import retrieve
from tests.test_mapping import atom
from tests.test_acceptance import _supported_nova_mapping

kb = load_knowledge(Path("knowledge/epoxy-2025.1"))
text = "Nova должна поддерживать квантовую телепортацию виртуальной машины."
result = accept_mapping(
    atom(text), retrieve(kb, text, (), 8), kb, _supported_nova_mapping()
)
print(result.support_status.value)
PY
```

На проверенном commit вывод — `supported`. После исправления этот случай
должен терять положительный статус при сохранении исходного обязательства.
Воспроизведение не проверяет возможность телепортации: оно проверяет отсутствие
её доказательства в cited evidence и реакцию валидатора.

ожидают `supported` на scope evidence. Это ожидание требует исправления:
для старого snapshot нужен отдельный случай нехватки доказательств, для
положительного сценария — детальное проверенное evidence и новый snapshot.
Установка ожидаемого `supported` только ради совпадения с ответом недопустима.

Deep gold проверяет архитектуру на synthetic fixtures. Production deep corpus
не поставляется; переключение профиля само по себе не заполняет пробелы.
Ранее выполненная [живая проверка VS Code](2026-10-05-vscode-codex-live.md)
остаётся единственным выполненным IDE-сценарием и не заменяется этим аудитом.
